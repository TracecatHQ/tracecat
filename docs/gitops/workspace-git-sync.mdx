## Overview

Use Git sync to export workspace configuration to a repository you own as a pull request, then pull a reviewed commit into a workspace.

## Permissions

| Task | Built-in roles | Custom role scope |
| --- | --- | --- |
| Configure providers | `organization-admin`, `organization-owner` | `org:settings:update` |
| Connect or change a workspace repository | `workspace-admin` and above | `workspace:update` |
| Push | `workspace-editor` and above | `workspace_sync:push` |
| Pull | `workspace-admin` and above | `workspace_sync:pull` |

Viewers cannot sync.

## Connect a provider

<Steps>
  <Step title="Open organization Git providers">
    Open `Git providers` in the organization sidebar (`/organization/vcs`).

    <Frame>
      ![Organization Git providers with GitHub, GitLab, and Bitbucket connections](/img/manage-platform/git-sync-settings.png)
    </Frame>
  </Step>
  <Step title="Connect your provider">
    Click `Connect` on your provider, then follow its tab below.

    <Tabs>
      <Tab title="GitHub">
        - Create a GitHub App through the manifest flow, or enter the App ID and private key of an existing GitHub App.
        - Install the app under the account or organization that owns your repositories, and grant it access to them.
        - The `Create app` tab lists the URLs Tracecat writes into the manifest, each with a copy button for GitHub Enterprise allowlists or app review:

        | URL | Value |
        | --- | --- |
        | Redirect URL and callback URL | `<PUBLIC_APP_URL>/organization/vcs/github/install` |
        | Setup URL | `<PUBLIC_APP_URL>/organization/vcs` |
        | Webhook URL | `<PUBLIC_API_URL>/organization/vcs/github/webhook` |

        `PUBLIC_APP_URL` and `PUBLIC_API_URL` are your `TRACECAT__PUBLIC_APP_URL` and `TRACECAT__PUBLIC_API_URL` values. On a `localhost` deployment, Tracecat creates the webhook inactive with a placeholder URL.
      </Tab>
      <Tab title="GitLab">
        - Enter your GitLab base URL, such as `https://gitlab.example.com`.
        - Enter a project or group access token with both `api` and `write_repository` scopes. Personal access tokens with `api` already include Git write access; see [GitLab access token scopes](https://docs.gitlab.com/security/tokens/access_token_scopes/).
        - The worker pushes commits over Git-over-HTTPS and manages merge requests through the API.

        <Info>
          Upgrading an existing GitLab connection to durable Git sync? Replace an `api`-only project or group token with one that has both scopes first.
        </Info>
      </Tab>
      <Tab title="Bitbucket Cloud">
        - Click `Connect` (or `Manage`), then choose Cloud.
        - Enter your Atlassian account email and a [scoped API token](https://support.atlassian.com/bitbucket-cloud/docs/using-api-tokens/) with all four [permissions](https://support.atlassian.com/bitbucket-cloud/docs/api-token-permissions/): `read:repository:bitbucket`, `write:repository:bitbucket`, `read:pullrequest:bitbucket`, and `write:pullrequest:bitbucket`.
        - The account must have access to the repository, and the repository needs at least one commit before you sync.
      </Tab>
      <Tab title="Bitbucket Data Center">
        - Click `Connect` (or `Manage`), then choose Data Center.
        - Enter your HTTPS instance URL, including any port and context path, such as `https://bitbucket.example.com:8443/bitbucket`.
        - Enter an [HTTP access token](https://confluence.atlassian.com/bitbucketserver/http-access-tokens-939515499.html) with repository write permission.
      </Tab>
    </Tabs>

    Use `Update` to rotate a token before it expires. Deleting credentials disconnects sync across the organization; it preserves workspace resources, repository branches, and custom-registry credentials.
  </Step>
</Steps>

## Bind a workspace

<Steps>
  <Step title="Open workspace Git sync">
    Open `Git sync` in the workspace sidebar, then choose a `Provider` configured by your organization admin.
  </Step>
  <Step title="Connect the repository">
    Paste the repository's SSH clone URL and click `Connect`. For GitHub, you can also choose a repository from the GitHub App installation list.

    <Frame>
      ![Connect a repository with a GitLab provider and SSH clone URL](/img/manage-platform/git-sync-connect.png)
    </Frame>

    | Provider | Accepted URL |
    | --- | --- |
    | GitHub | `git@github.com:example-org/example-repo.git`, `ssh://git@github.com/example-org/example-repo.git`, or `git+ssh://git@github.com/example-org/example-repo.git` |
    | GitLab | `git@gitlab.example.com:example-org/example-repo.git` |
    | Bitbucket Cloud | `git@bitbucket.org:example-workspace/example-repo.git` |
    | Bitbucket Data Center | `git+ssh://git@bitbucket.example.com/PROJECT/repository.git` |

    - Tracecat rejects HTTPS repository URLs and bare paths such as `example-org/example-repo`.
    - For Bitbucket Data Center, the hostname must match the configured instance. Tracecat uses HTTPS with your HTTP access token for Git and API requests.
  </Step>
</Steps>

### Change the connection

Click `Edit` beside the repository name.

- `Branch` sets the base branch for new exports and the commit list for pulls. A stored URL ending in `@branch` pins that branch; without the suffix, Tracecat uses the repository default.
- `Change` edits the SSH URL. Click `Save` to apply it. Changing the repository or pinned branch clears the current previews.
- `Disconnect` stops push and pull until you connect a repository again. It preserves workspace and repository content.

<Frame>
  ![Repository connection editor with an SSH URL, branch selector, and disconnect action](/img/manage-platform/git-sync-edit-repository.png)

## What an export contains

A full export writes `tracecat.json` plus one folder per resource type. Here is a workspace with three workflows, two tables, two variables, a secret, case tags, and case fields after its first push:

```text
example-repo/
├── tracecat.json                    # Manifest: resource type → folder
├── workflows/
│   ├── Daily-alert-digest/
│   │   └── definition.yml
│   ├── Enrich-IP-address/
│   │   ├── definition.yml
│   │   └── scripts/score_ip.py      # One file per Python action
│   └── Triage-phishing-alerts/
│       ├── definition.yml
│       └── scripts/extract_iocs.py
├── tables/
│   ├── asset_inventory/table.yml    # Schema only, no rows
│   └── indicators/table.yml
├── variables/
│   └── default/                     # Workflow environment
│       ├── slack.yml
│       └── threat_intel.yml
├── secret_metadata/
│   └── default/threat_intel.yml     # Keys only, no values
├── case_fields/
│   ├── affected_hosts.yml
│   └── reporter_email.yml
└── case_tags/
    └── _all.yml                     # Every tag in one file
```

<Frame caption="The same export in GitLab after the merge request merges.">
  ![GitLab repository tree with tracecat.json and folders for workflows, tables, variables, secret metadata, case fields, and case tags](/img/manage-platform/git-sync-repo-tree.png)

Exports also include agent presets, skills, case dropdowns, and case durations when the workspace has them. Tracecat excludes schedules.

### File names and identity

- Tracecat names each folder or file after the resource's current name: workflows after their title, agent presets and skills after their slug, and variables and secret metadata after their environment and name.
- The `id` field inside each file identifies the resource. Renaming a resource moves its file on the next push, and a pull updates the same resource in place.
- When two resources of one type share a name, the one that already holds the path keeps it, and Tracecat appends the `id` to the other: `workflows/Triage-alerts-wf_4f2a.../definition.yml`. If neither has been pushed, the lower `id` gets the plain name. A resource keeps its path, suffix included, until you rename it.
- Case tags share one `case_tags/_all.yml` file, listed under `tags`.

<Warning>
  Keep each `id` unique. A pull rejects two files with the same `id`, so duplicate a resource in Tracecat instead of copying its folder. If two branches rename the same resource and both merge, push that resource from Tracecat to remove the extra copy.
</Warning>

### Workflow scripts

- Tracecat writes the script of each `core.script.run_python` action to `workflows/<workflow>/scripts/<ref>.py`. The action in `definition.yml` keeps its other arguments and has no `script` key.
- Edit the `.py` file to change a script; a pull reads it back into the action. An action with no script, such as an empty Python step in a draft, gets no file.
- If you rename an action's `ref`, rename its script file too. A pull fails on any `.py` file in `scripts/` that matches no Python action, and names the file.
- Pushing a workflow deletes every file in its folder that Tracecat does not write, so keep your own notes outside `workflows/`.

### Configuration, not data

| Resource | Exported | Not exported |
| --- | --- | --- |
| Forms | A [`form:` block](/automations/triggers/forms#git-sync) in the workflow's `definition.yml` | Submissions |
| Tables | Column schema | Rows |
| Variables | Key names | Values |
| Secrets | Metadata | Values |
| Schedules | — | Everything |

- A secret file with a `value` or `values` key fails import.
- [Externally backed secrets](/automations/core-concepts/external-secret-stores) also export their store name, remote reference (a secret name, ARN, or ID), and key mapping. If the target workspace has no authorized store with that name, the pull preview asks you to choose one for every secret that uses it.

### Repositories from earlier versions

Earlier versions named paths by `id` (such as `workflows/wf_4f2a.../definition.yml` or `case_tags/<id>.yml`), kept one file per case tag, and wrote scripts inline in `definition.yml`.

- Pulls still read these layouts. An inline script wins over a script file for the same action.
- The next push moves each resource it writes to its readable path, or into `case_tags/_all.yml`, and deletes the old file.
- A push of selected resources keeps every other tag in `case_tags/_all.yml`. A full push replaces the file with your workspace's tags, deleting tags that exist only on the branch.

<Warning>
  Upgrade every Tracecat instance that uses a repository before you push to it. Earlier versions reject readable paths and `case_tags/_all.yml`, import Python actions without their script files, and can leave stale script files that fail later pulls.
</Warning>
