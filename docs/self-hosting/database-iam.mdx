With `TRACECAT__DB_AUTH_MODE` set to `aws_iam` or `azure_entra`, each Tracecat service signs a short-lived token with its own cloud identity and sends it as the database password. Every new connection gets a valid token, so no service holds a database password. The default, `password`, keeps the existing password login. [Redis](#redis) has the same modes in `REDIS_AUTH_MODE`.

## Settings

A token mode connects with these variables and refuses to start if `TRACECAT__DB_PASS`, `TRACECAT__DB_PASS__ARN` or `TRACECAT__DB_URI` is set:

| Variable | Value |
|----------|-------|
| `TRACECAT__DB_AUTH_MODE` | `aws_iam` or `azure_entra` |
| `TRACECAT__DB_USER` | The database user, such as `app` |
| `TRACECAT__DB_ENDPOINT` | The host Tracecat connects to: the database, or PgDog |
| `TRACECAT__DB_PORT` | Its port, such as `5432` (or `6432` for PgDog) |
| `TRACECAT__DB_NAME` | The database name, such as `tracecat` |
| `TRACECAT__DB_SSLMODE` | `require`, `verify-ca` or `verify-full` |

`require` encrypts the connection without checking the server's certificate, and `verify-ca` checks the certificate's CA but not the host name, so any certificate from that CA passes. Only `verify-full` checks that the server is the host you named. For a direct connection to the database, use `verify-full` and point `PGSSLROOTCERT` at the CA bundle, such as the [RDS global bundle](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem) or `/etc/ssl/certs/ca-certificates.crt` for Azure.

`aws_iam` also reads `TRACECAT__DB_AWS_REGION` (default `AWS_REGION`) and `TRACECAT__DB_AWS_IAM_HOST` / `TRACECAT__DB_AWS_IAM_PORT`, the RDS endpoint the token is signed for (default `TRACECAT__DB_ENDPOINT` / `TRACECAT__DB_PORT`). `azure_entra` reads `TRACECAT__DB_AZURE_CLIENT_ID`, the managed identity's client ID (default `AZURE_CLIENT_ID`).

## Amazon RDS

<Steps>
  <Step title="Turn on IAM database authentication">
    ```bash
    aws rds modify-db-instance --db-instance-identifier <instance-id> \
      --enable-iam-database-authentication --apply-immediately
    ```
  </Step>
  <Step title="Create the database user">
    As the master user, create the login and grant it `rds_iam`:

    ```sql
    CREATE ROLE app LOGIN;
    GRANT rds_iam TO app;
    ```

    `rds_iam` turns off a role's password login, so never grant it to the master user. With [database roles](/self-hosting/database-roles), `tracecat db roles upgrade --login aws_iam` creates `app`, `migrator` and `agent_runtime` and grants them `rds_iam` for you.
  </Step>
  <Step title="Allow each service's IAM role to connect">
    Look up the instance's resource ID, which looks like `db-ABCDEFGHIJKLMNOPQRSTUVWXYZ`:

    ```bash
    aws rds describe-db-instances --db-instance-identifier <instance-id> \
      --query 'DBInstances[0].DbiResourceId' --output text
    ```

    Attach this statement to every IAM role a Tracecat service runs as (IRSA or Pod Identity on EKS, the task role on ECS). The resource is the `rds-db` user ARN, not the instance ARN:

    ```json
    {
      "Effect": "Allow",
      "Action": "rds-db:connect",
      "Resource": "arn:aws:rds-db:<region>:<account-id>:dbuser:<DbiResourceId>/app"
    }
    ```

    Every pod or task on that role can then log in as `app`, including executors that run workflow actions. Never grant it to the node's instance role: every pod on the node could then log in as `app`. On EKS, set `AWS_EC2_METADATA_DISABLED=true` on Tracecat's pods so a pod without its own identity fails instead of signing with the node role (the Helm chart sets it).
  </Step>
  <Step title="Configure Tracecat">
    Download the RDS CA bundle and mount it into every Tracecat container, here at `/etc/tracecat/rds-global-bundle.pem` (a Kubernetes ConfigMap or Secret volume, or an ECS bind mount):

    ```bash
    curl -fsSLo rds-global-bundle.pem https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem
    ```

    ```bash
    TRACECAT__DB_AUTH_MODE=aws_iam
    TRACECAT__DB_USER=app
    TRACECAT__DB_ENDPOINT=<instance-id>.<hash>.<region>.rds.amazonaws.com
    TRACECAT__DB_PORT=5432
    TRACECAT__DB_NAME=tracecat
    TRACECAT__DB_SSLMODE=verify-full
    PGSSLROOTCERT=/etc/tracecat/rds-global-bundle.pem
    TRACECAT__DB_AWS_REGION=<region>
    ```
  </Step>
</Steps>

Tracecat signs each token locally with the service's AWS credentials and reuses it for 10 minutes of its 15-minute life. RDS checks the token only at login, so open connections outlive it.

## Azure Database for PostgreSQL

<Steps>
  <Step title="Turn on Microsoft Entra authentication">
    On the flexible server, enable Microsoft Entra authentication and set an Entra administrator. On AKS, turn on the cluster's OIDC issuer and Workload Identity.
  </Step>
  <Step title="Create a managed identity for Tracecat">
    Create a user-assigned managed identity for `app` and federate it with each Kubernetes service account that Tracecat runs as (Workload Identity). Run this once per service account, with a credential name unique to each:

    ```bash
    az identity federated-credential create --name <service-account> \
      --identity-name <identity-name> --resource-group <resource-group> \
      --issuer <aks-oidc-issuer-url> \
      --subject system:serviceaccount:<namespace>:<service-account>
    ```

    Note the identity's client ID and object ID; the next steps use both:

    ```bash
    az identity show --name <identity-name> --resource-group <resource-group> \
      --query '{clientId: clientId, objectId: principalId}'
    ```

    Label the pods `azure.workload.identity/use: "true"` and give them the client ID, in `TRACECAT__DB_AZURE_CLIENT_ID` or the service account annotation `azure.workload.identity/client-id`. Never assign the identity to the node pool: every pod on the node could then log in as `app`.
  </Step>
  <Step title="Create the database users">
    As the Entra administrator, connected to the `postgres` database, map each database role to the object ID of the identity that logs in as it:

    ```sql
    SELECT * FROM pgaadauth_create_principal_with_oid('app', '<app-object-id>', 'service', false, false);
    ```

    With [database roles](/self-hosting/database-roles) (`tracecat db roles upgrade --login azure_entra`), create all three login roles first; role setup then grants their privileges. `migrator` maps to the migrations Job's identity and `app` to the services' identity. The agent runtime logs in as `app` too. Role setup needs `agent_runtime` to exist, but nothing logs in as it yet, so map it to an identity of its own that no workload uses:

    ```sql
    SELECT * FROM pgaadauth_create_principal_with_oid('migrator', '<migrations-object-id>', 'service', false, false);
    SELECT * FROM pgaadauth_create_principal_with_oid('app', '<app-object-id>', 'service', false, false);
    SELECT * FROM pgaadauth_create_principal_with_oid('agent_runtime', '<runtime-object-id>', 'service', false, false);
    ```
  </Step>
  <Step title="Configure Tracecat">
    ```bash
    TRACECAT__DB_AUTH_MODE=azure_entra
    TRACECAT__DB_USER=app
    TRACECAT__DB_ENDPOINT=<server-name>.postgres.database.azure.com
    TRACECAT__DB_PORT=5432
    TRACECAT__DB_NAME=tracecat
    TRACECAT__DB_SSLMODE=verify-full
    PGSSLROOTCERT=/etc/ssl/certs/ca-certificates.crt
    TRACECAT__DB_AZURE_CLIENT_ID=<app-client-id>
    ```
  </Step>
</Steps>

Tracecat gets tokens from `DefaultAzureCredential`, which caches each token and renews it before it expires.

## Kubernetes with PgDog

The Helm chart's `externalPostgres.auth.mode` takes `awsIam` or `azureWorkloadIdentity`. Every Tracecat workload, the agent runtime included, then signs its own token and logs in to PgDog, which passes the token through to the database. PgDog's user takes `auth_type = "external_token"`: PgDog checks each new token once by logging in to the database with it, as `pgdog.serverUser`, so `serverUser` must be the workloads' username. The migrations Job logs in directly, as `migrator` with a token of its own (see [Migrations](#migrations)).

Both modes need:

- PgDog v0.1.65 or newer, which has the token-cache fix (pgdog#1989). Set `pgdog.image.tag` if your chart's default is older.
- `externalPostgres.sslMode: require` or stricter, and `externalPostgres.tls.verifyCA` with the database's CA in `caCert`.
- `agentRuntime.durable.database.dsnSecret` left empty, so the agent runtime logs in as the workloads do.

Clients reach PgDog over TLS that doesn't verify PgDog's certificate. A token taken from that hop is accepted by the database until it expires, and PgDog accepts it for 15 minutes after it first sees it.

### RDS IAM

The chart signs the tokens for `externalPostgres.host`, so set it to the RDS endpoint.

```yaml
externalPostgres:
  host: <instance-id>.<hash>.<region>.rds.amazonaws.com
  sslMode: require
  auth:
    mode: awsIam
    awsIam:
      username: app
  tls:
    verifyCA: true
    caCert: |
      ...RDS CA bundle...

pgdog:
  enabled: true
  serverAuth: rds_iam
  serverUser: app
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/tracecat-pgdog

migrations:
  migrator:
    enabled: true
    login: aws_iam
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/tracecat-migrator
```

### Azure Workload Identity

Azure maps each Entra identity to one Postgres role, and PgDog checks the workloads' tokens as `serverUser`. So the workloads and PgDog share the one identity mapped to `app`, with a federated credential for each service account. The migrations Job uses `migrator`'s own identity.

```yaml
externalPostgres:
  host: <server-name>.postgres.database.azure.com
  sslMode: require
  auth:
    mode: azureWorkloadIdentity
    azureWorkloadIdentity:
      username: app
      clientId: <app-client-id>
  tls:
    verifyCA: true
    caCert: |
      ...DigiCert Global Root G2 and Microsoft RSA Root Certificate Authority 2017...

pgdog:
  enabled: true
  serverAuth: azure_workload_identity
  serverUser: app
  serviceAccount:
    annotations:
      azure.workload.identity/client-id: <app-client-id>

migrations:
  migrator:
    enabled: true
    login: azure_entra
  serviceAccount:
    annotations:
      azure.workload.identity/client-id: <migrator-client-id>
```

The chart labels every pod that logs in this way with `azure.workload.identity/use: "true"` and passes `clientId` to the workloads in `TRACECAT__DB_AZURE_CLIENT_ID`. Get `caCert` from Microsoft's [TLS certificates for Azure Database for PostgreSQL](https://learn.microsoft.com/azure/postgresql/flexible-server/concepts-networking-ssl-tls).

Federate the `app` identity with every service account the release's workloads and PgDog run as, and the `migrator` identity with the migrations Job's. List them from your values:

```bash
helm template tracecat tracecat/tracecat -f values.yaml \
  | yq 'select(.kind == "ServiceAccount") | .metadata.name'
```

The workloads use `<release>-app` unless you create dedicated service accounts, PgDog uses `<release>-pgdog` and the migrations Job `<release>-migrations`.

## Migrations

Without database roles, the migrations Job logs in with `externalPostgres.auth.existingSecret`. With them, it logs in as `migrator` (`migrations.migrator`, with `login: aws_iam` or `login: azure_entra` for a token of its own) and never as the admin; see [Database roles](/self-hosting/database-roles). The token modes need `migrations.migrator`. The `tracecat-admin migrate` commands take a password URI only.

## Redis

With `REDIS_AUTH_MODE` set to `aws_iam` or `azure_entra`, Tracecat logs in to Redis with a token from its cloud identity and renews it before it expires. Tracecat then needs a `rediss://` URL with no username or password.

### Azure Managed Redis

<Steps>
  <Step title="Create the cache with access keys off">
    Create the cache with TLS on (`Encrypted`) and access keys off. Entra authentication works over TLS only, and Microsoft turns it on by default. Tracecat's Redis client needs the `EnterpriseCluster` clustering policy.

    ```bash
    az redisenterprise create --cluster-name <cache-name> \
      --resource-group <resource-group> --location <region> --sku <sku> \
      --client-protocol Encrypted --clustering-policy EnterpriseCluster \
      --access-keys-auth Disabled --port 10000
    ```

    `<sku>` is a size such as `Balanced_B1`. On an existing cache, turn access keys off on its `default` database.
  </Step>
  <Step title="Allow the app identity">
    Assign the default access policy to the object ID of the identity mapped to `app` (see [Azure Database for PostgreSQL](#azure-database-for-postgresql)):

    ```bash
    az redisenterprise database access-policy-assignment create \
      --cluster-name <cache-name> --resource-group <resource-group> \
      --database-name default --access-policy-assignment-name tracecat-app \
      --access-policy-name default --object-id <app-object-id>
    ```
  </Step>
  <Step title="Configure Tracecat">
    ```bash
    REDIS_AUTH_MODE=azure_entra
    REDIS_URL=rediss://<cache-name>.<region>.redis.azure.net:10000
    REDIS_AZURE_CLIENT_ID=<app-client-id>
    ```

    With the Helm chart, list the components that log in this way instead of setting the URL Secret. `clientId` defaults to `externalPostgres.auth.azureWorkloadIdentity.clientId`:

    ```yaml
    externalRedis:
      auth:
        azureWorkloadIdentity:
          components: [api, worker, backgroundWorker, agentWorker, mcp, executor, agentExecutor, runtimeWorker, runtimeExecutor, toolGateway]
          host: <cache-name>.<region>.redis.azure.net
          port: 10000
    ```
  </Step>
</Steps>

On Azure Cache for Redis, turn on Microsoft Entra authentication, turn off access keys and add a data access policy assignment for the same object ID. Its host is `<cache-name>.redis.cache.windows.net` and its TLS port is `6380`.

### Amazon ElastiCache

`aws_iam` logs each component in as its own ElastiCache IAM user, on a replication group (ElastiCache Serverless isn't supported). Set `REDIS_AWS_IAM_USER_ID`, `REDIS_AWS_IAM_REPLICATION_GROUP_ID` and `REDIS_AWS_REGION`; the Helm chart sets them per component from `externalRedis.auth.awsIam`. See [Environment variables](/self-hosting/environment-variables) for their formats.

## Limitations

- The AWS Fargate Terraform doesn't set `TRACECAT__DB_AUTH_MODE` yet; Fargate deployments keep password login.
- Self-hosted Temporal still logs in to its own database with a password. A fully passwordless install needs Temporal Cloud or another external Temporal.
