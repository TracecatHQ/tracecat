## Overview

Use Git sync to export workspace configuration to a repository you own as a pull request, then pull a reviewed commit into a workspace.

## Permissions

Organization admins configure providers. Workspace admins connect or change a workspace repository. Workspace editors can push and pull from an existing connection; viewers cannot sync.

For custom roles, provider setup requires `org:settings:update`, changing the workspace connection requires `workspace:update`, and the workspace Git sync page requires `workspace_sync:sync` to push and pull.

## Connect a provider

<Steps>
  <Step title="Open organization Git providers">
    Open `Git providers` in the organization sidebar (`/organization/vcs`).

    <Frame>
      ![Organization Git providers with GitHub, GitLab, and Bitbucket connections](/img/manage-platform/git-sync-settings.jpg)
    </Frame>
  </Step>
  <Step title="Connect your provider">
    For GitHub, click `Connect`, then create a GitHub App through the manifest flow or enter the ID and private key of an existing GitHub App. Install it on the repositories you want to sync.

    For GitLab, click `Connect`, then enter your base URL and a project or group access token with the `api` scope.

    For Bitbucket, click `Connect` (or `Manage` for an existing connection) to choose Cloud or Data Center.

    For Cloud, click `Connect`, then enter your Atlassian account email and a [scoped API token](https://support.atlassian.com/bitbucket-cloud/docs/using-api-tokens/). Select all four [permissions](https://support.atlassian.com/bitbucket-cloud/docs/api-token-permissions/):

    - `read:repository:bitbucket`
    - `write:repository:bitbucket`
    - `read:pullrequest:bitbucket`
    - `write:pullrequest:bitbucket`

    The account must have access to the repository. Initialize the repository with a commit before syncing. For Bitbucket Data Center, click `Connect` on the Data Center connection with your HTTPS instance URL and an [HTTP access token](https://confluence.atlassian.com/bitbucketserver/http-access-tokens-939515499.html) granting repository write permission. Include any port and context path in the instance URL, such as `https://bitbucket.example.com:8443/bitbucket`.

    Use `Update` to rotate the token before it expires. Deleting these credentials disconnects sync across the organization; it preserves workspace resources, repository branches, and custom-registry credentials.
  </Step>
</Steps>

## Bind a workspace

<Steps>
  <Step title="Open workspace Git sync">
    Open `Git sync` in the workspace sidebar, then choose a `Provider` configured by your organization admin.
  </Step>
  <Step title="Connect the repository">
    Paste the repository's SSH clone URL and click `Connect`. For GitHub, you can also choose a repository from the GitHub App installation list.

    Use `git@github.com:example-org/example-repo.git`, `ssh://git@github.com/example-org/example-repo.git`, or `git+ssh://git@github.com/example-org/example-repo.git`. HTTPS repository URLs and bare paths such as `example-org/example-repo` are not accepted.

    For Bitbucket Cloud, use `git@bitbucket.org:example-workspace/example-repo.git`. For Data Center, use `git+ssh://git@bitbucket.example.com/PROJECT/repository.git`. Its hostname must match the configured instance. Put the port and context path in the organization instance URL; Tracecat uses HTTPS with your HTTP access token for Git and API requests.

    <Frame>
      ![Connect a repository with a GitLab provider and SSH clone URL](/img/manage-platform/git-sync-connect.jpg)
    </Frame>
  </Step>
</Steps>

### Change the connection

Click `Edit` beside the repository name. Use `Branch` to choose the base branch for new exports and the commit list for pulls. A stored URL ending in `@branch` pins that branch; a URL without the suffix uses the repository default.

Click `Change` beside the repository to edit its SSH URL, then `Save`. Changing the repository or pinned branch clears the current previews. `Disconnect` stops push and pull until you connect a repository again; it preserves workspace and repository content.

<Frame>
  ![Repository connection editor with an SSH URL, branch selector, and disconnect action](/img/manage-platform/git-sync-edit-repository.jpg)
</Frame>

## What an export contains

A full export writes `tracecat.json` and one directory per resource type: workflows, agent presets, skills, tables, case fields, case tags, case dropdowns, case durations, variables, and secret metadata. Tracecat writes each workflow to `workflows/<id>/definition.yml` and excludes schedules.

A workflow's [form](/automations/triggers/forms) exports inside the workflow's file as a `form:` block that holds the form config and its `status`. Tracecat writes the block when the form is online or has any config.

```yaml
form:
  status: online
  title: Laptop request
  layout:
    - field: model
      widget: cards
```

Exports carry configuration, not data:

- Forms export their config and no submissions or activity.
- Tables export their column schema and no rows.
- Variables export key names and no values.
- Secrets export metadata only; a secret file with a `value` or `values` key fails import.
  [AWS-backed secrets](/automations/core-concepts/external-secret-stores) also export
  their store name, secret name or ARN, and key mapping. If the target workspace
  has no authorized store with that name, the pull preview asks you to choose one.
  The choice applies to every secret that uses that store name.

## Push and open a pull request

Use the `Push` tab to push the full workspace configuration.

<Steps>
  <Step title="Choose a branch and commit message">
    On the `Push` tab, use the branch picker beside `Into` to choose an existing branch or enter a new branch name and click `Create`. Enter a commit message. New branches start from the base branch. Tracecat blocks direct pushes to both the base branch and the repository default branch.

    <Frame>
      ![Git sync Push tab with grouped resource changes, target branch, and commit message](/img/manage-platform/git-sync-workspace-push.jpg)
    </Frame>
  </Step>
  <Step title="Preview changes">
    Click `Preview` to compare with the target branch, or the base branch when creating a branch. Expand a resource group to review its file changes. Use `Preview again` after making more edits.
  </Step>
  <Step title="Push">
    Click `Push and open PR` (`Push and open MR` on GitLab); the button includes the change count after a preview. Use the adjacent menu to choose `Push only` when you want a commit without a pull request. Tracecat commits only changed files, deletes stale files, and reuses an open pull request on the same branch.

    The pull request body names the workspace and the publishing user's email.
  </Step>
</Steps>

## Pull a commit

A merged pull request changes nothing in a workspace until you or your pipeline pull that commit.

<Steps>
  <Step title="Choose a commit">
    On the `Pull` tab, use the commit picker beside `From` to choose a commit from the base branch.

    <Frame>
      ![Git sync Pull tab with grouped changes, commit selector, and schedule-overwrite control](/img/manage-platform/git-sync-workspace-pull.jpg)
    </Frame>
  </Step>
  <Step title="Preview changes">
    Click `Preview` to dry-run the pull. If Tracecat cannot resolve a model, MCP integration, or secret store, choose its target in the matching dialog, then click `Save and preview again`. Use `Choose matches` to reopen unresolved choices. Resolve any validation errors before pulling.

    <Frame>
      ![Match model and MCP references before pulling a commit](/img/manage-platform/git-sync-manual-matching.jpg)
    </Frame>
  </Step>
  <Step title="Apply">
    Click `Pull into <workspace>`; the button includes the change count after a preview. Tracecat enables it only after a successful preview for the same commit and options. A pull updates matching workspace resources and leaves schedules untouched unless you check `Overwrite schedules`. Changing the commit, schedule option, or reference matches requires another preview.
  </Step>
</Steps>

<Warning>
  A pull can overwrite local edits made after the preview. Coordinate workspace edits, run one push or pull at a time, and wait for it to finish before starting another. Leaving the page does not cancel an in-flight sync. A push exports the workspace state when you submit it, so preview again after editing resources.
</Warning>

A pull creates or replaces a workflow's form from the `form:` block in its file; a block without `status` leaves the form offline. When the file has no `form:` block, the pull sets the workflow's existing form offline and clears its config; the form keeps its ID and submissions. A block that no longer matches the workflow's inputs does not fail the pull: Tracecat stores it as written, and the form stops accepting submissions until you fix it.

An instance on a version without Forms writes `definition.yml` without the `form:` block, so its push removes the block and the next pull on a newer instance takes the form offline. Upgrade every instance that pushes to the repository before you build forms in it.

Until you publish a pulled workflow, its runs resolve actions against the workspace's current registry versions. Publishing it records the registry lock.

## Staging to production

<Steps>
  <Step title="Bind both workspaces">
    Bind staging and production workspaces to the same repository. Role assignments are per workspace, so grant `workspace_sync:sync` (`workspace-editor` and above) in each.
  </Step>
  <Step title="Push from staging">
    Build in staging, then choose `Push and open PR` (`MR` on GitLab) from its `Push` tab.
  </Step>
  <Step title="Review and merge">
    Merge the pull request in your repository, where branch protection and required reviews apply.
  </Step>
  <Step title="Pull into production">
    In production, select the merged commit, click `Preview`, then `Pull into <workspace>`. Publish any workflow that needs a registry lock.
  </Step>
</Steps>

## API reference

Exporting a workspace requires `workspace_sync:sync`. Reading branches and commits, pulling, and publishing one workflow also accept `workflow:sync`, so a service account holding only `workflow:sync` can pull from CI.

| Action | Endpoint | Scopes |
| --- | --- | --- |
| Save provider credentials | `POST /organization/vcs/{provider}/credentials` (`github` or `gitlab`) | `org:settings:update` |
| Bind a repository | `PATCH /workspaces/{workspace_id}` with `settings.git_provider` and `settings.git_repo_url` | `workspace:update` |
| Preview an export | `POST /workflows/sync/export/preview` | `workspace_sync:sync` |
| Export and open a pull request | `POST /workflows/sync/export` | `workspace_sync:sync` |
| Push one workflow | `POST /workflows/{workflow_id}/publish` | `workflow:update`, plus `workflow:sync` or `workspace_sync:sync` |
| List branches and commits | `GET /workflows/sync/branches`, `GET /workflows/sync/commits?branch=` | `workflow:sync` or `workspace_sync:sync` |
| Pull a commit | `POST /workflows/sync/pull` with a required `commit_sha` | `workflow:sync` or `workspace_sync:sync` |
