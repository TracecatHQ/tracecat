## Overview

A tunnel lets actions in one workspace reach hosts on a private network without opening inbound firewall ports. Tracecat uses [Pangolin](https://docs.pangolin.net):

- A site connector (Newt) runs inside your network and opens an outbound tunnel to the Pangolin server.
- Pangolin grants the tunnel's machine client access to each allowed target, on its listed TCP ports only. UDP and ICMP are off.
- A tunnel gateway runs the machine client and forwards action traffic. It accepts only short-lived tokens for its own tunnel and workspace, connects only to the tunnel's allowed targets, and logs every connection.

Tunnels belong to one workspace. Every lookup, update, delete, and status check is scoped to the workspace in the request, so one workspace cannot read or use another workspace's tunnel.

Actions use a tunnel when you select it on the action or as the workflow's default tunnel. See [Route actions through a tunnel](#route-actions-through-a-tunnel).

## Requirements

- The `tunnels` Enterprise entitlement.
- `tunnel:read` to list tunnels and check status, and `tunnel:create`, `tunnel:update`, or `tunnel:delete` to manage them. Workspace admins and organization owners and admins hold all four; workspace viewers hold `tunnel:read`.
- A Pangolin server: Pangolin Cloud for Tracecat Cloud, or your own Pangolin deployment for self-hosted Tracecat. See [Configure Pangolin for self-hosted Tracecat](#configure-pangolin-for-self-hosted-tracecat).

## Set up a tunnel from start to finish

This guide takes you from nothing to a workflow that calls an internal URL, using an on-premises Splunk at `https://splunk.internal:8089` as the example. On Tracecat Cloud you only run the site connector inside your network; Tracecat runs the gateway.

### Before you start

- The `tunnels` entitlement and the `tunnel:create` scope in the workspace.
- The internal hostname or IP address and TCP port of each service, such as `splunk.internal:8089`.
- A Linux host inside your network, with Docker or the ability to run a binary, that can resolve and reach every service. It needs outbound access to the Pangolin endpoint, `https://app.pangolin.net` on Tracecat Cloud, and no inbound ports. The connector uses TCP 443 and UDP 51820 to the Pangolin endpoint.
- The PEM-encoded CA certificate if an internal CA signs the service's certificate.

<Steps>
  <Step title="Create the tunnel">
    In the workspace sidebar, open **Tunnels** and select **Create tunnel**. Enter a name, such as `onprem-splunk`, and list one target per line as `host:port`, or `host:port,port` for several ports. Use the exact hostname your workflows will call; wildcards and CIDR ranges are rejected. Select **Create tunnel**.

    <Frame>
      <img src="/img/manage-platform/tunnels-create.png" alt="Create a tunnel with splunk.internal:8089 as the target" />
    </Frame>
  </Step>
  <Step title="Copy the site connector credentials">
    Tracecat shows the site connector command once. It contains the site ID, the site secret, and the Pangolin endpoint. Copy it, and store the secret in your secrets manager.

    <Frame>
      <img src="/img/manage-platform/tunnels-install-command.png" alt="One-time site connector command" />
    </Frame>
  </Step>
  <Step title="Run the site connector on your host">
    On the host inside your network, run the connector (Newt) with the values from the command. With Docker:

    ```bash
    docker run -d --name tracecat-tunnel --restart unless-stopped \
      -e PANGOLIN_ENDPOINT=https://app.pangolin.net \
      -e NEWT_ID=<site_id> \
      -e NEWT_SECRET=<site_secret> \
      fosrl/newt
    ```

    Without Docker, install the `newt` binary from the [Newt releases](https://github.com/fosrl/newt/releases) and run the copied command, `newt --id <site_id> --secret <site_secret> --endpoint https://app.pangolin.net`, under a service manager such as systemd so it restarts with the host.
  </Step>
  <Step title="Check the tunnel status">
    Back on the **Tunnels** page, the tunnel shows **Site online** once the connector connects and **Gateway ready** once Tracecat's gateway for the tunnel is running. Both must be green before actions can use the tunnel.

    <Frame>
      <img src="/img/manage-platform/tunnels-status.png" alt="Tunnel status on the Tunnels page" />
    </Frame>
  </Step>
  <Step title="Add your internal CA">
    If an internal CA signs the service's certificate, open **Credentials**, select **Add credential**, name it `ca_cert`, set **Type** to **CA certificate**, and paste the PEM certificate. See [Use TLS with private services](#use-tls-with-private-services).
  </Step>
  <Step title="Call the internal URL from a workflow">
    In a workflow, add a **HTTP request** (`core.http_request`) action. Set **URL** to the internal URL, such as `https://splunk.internal:8089/services/server/info?output_mode=json`, and **Method** to `GET`. In the action's **Control flow** tab, set **Tunnel** to `onprem-splunk`.

    <Frame>
      <img src="/img/manage-platform/tunnels-action-tunnel.png" alt="Tunnel selected in the action's Control flow tab" />
    </Frame>

    To route every action in the workflow, set **Default tunnel** in the workflow settings instead. An action's own **Tunnel** overrides the default.

    <Frame>
      <img src="/img/manage-platform/tunnels-workflow-default.png" alt="Default tunnel in the workflow settings" />
    </Frame>
  </Step>
  <Step title="Run the workflow">
    Save, then run the workflow. The action's result shows the response from the internal service.

    <Frame>
      <img src="/img/manage-platform/tunnels-http-result.png" alt="Successful HTTP request through the tunnel" />
    </Frame>
  </Step>
</Steps>

### Run a Splunk search through the tunnel

Integration actions that make HTTP requests, such as **Splunk: Search events** (`tools.splunk.search_events`), use the tunnel the same way.

<Steps>
  <Step title="Add the Splunk credential">
    In **Credentials**, add a credential named `splunk` with the key `SPLUNK_API_KEY` set to a Splunk authentication token.
  </Step>
  <Step title="Add the search action">
    Add **Splunk: Search events**. Set `base_url` to `https://splunk.internal:8089`, `query` to a search that starts with `search`, such as `search index=main | head 10`, and the start and end times. In the **Control flow** tab, set **Tunnel** to `onprem-splunk`, or rely on the workflow's **Default tunnel**.
  </Step>
  <Step title="Run the workflow">
    The action returns the search results.

    <Frame>

    </Frame>
  </Step>
</Steps>

### Troubleshoot

| Symptom | Fix |
| :------ | :-- |
| The site stays offline. | Check that the connector is running and that the host can reach the Pangolin endpoint. Check the connector logs with `docker logs tracecat-tunnel`. |
| Saving or publishing fails with a tunnel error. | Check that the tunnel name matches a tunnel in this workspace and that the action supports tunnels. |
| The action fails with `403`. | Add the host and port to the tunnel's allowed targets. Managed tunnels can't change targets, so create a new tunnel. Use the same hostname in the URL as in the target. |
| The action fails with `504`. | The connector host can't reach the target. From that host, check that the hostname resolves and the port is open. |
| The action fails with `503`, or the gateway isn't ready. | The gateway can't load the tunnel's policy. Check that the tunnel is turned on and wait for the gateway to start. |
| The action fails with a certificate error. | Add the internal CA as `ca_cert` and use the hostname on the certificate. Keep `verify_ssl` set to `true`. |

## Create a managed tunnel with the API

Call the API with a [service account API key](/api-reference/authentication) and pass `workspace_id` as a query parameter on every request.

<Steps>
  <Step title="Create the tunnel">
    List every private host the workspace may reach, with its exact TCP ports:

    ```bash
    curl -X POST "https://<tracecat-host>/api/tunnels/managed?workspace_id=<workspace_id>" \
      -H "Authorization: Bearer <api_key>" \
      -H "Content-Type: application/json" \
      -d '{
        "name": "onprem-splunk",
        "description": "Splunk management API in the primary data center",
        "allowed_targets": [
          {"host": "splunk.internal", "ports": [8089]},
          {"host": "10.20.0.15", "ports": [8089]}
        ]
      }'
    ```

    `host` is an exact hostname or IP address; wildcards and CIDR ranges are rejected. Each target takes 1 to 64 unique ports, and a tunnel takes up to 100 targets.

    Tracecat creates a Pangolin site, one machine client for the tunnel, and one private resource per target granted only to that client. If any step fails, Tracecat deletes what it created and returns `502`.
  </Step>
  <Step title="Save the site credentials">
    The `201` response returns the site credentials once:

    ```json
    {
      "tunnel": {"id": "<tunnel_id>", "name": "onprem-splunk", "managed": true, "...": "..."},
      "site_id": "<site_id>",
      "site_secret": "<site_secret>",
      "site_endpoint": "https://app.pangolin.net",
      "site_install_command": "newt --id <site_id> --secret <site_secret> --endpoint https://app.pangolin.net"
    }
    ```

    Store `site_secret` in your secrets manager. Tracecat does not return it again.
  </Step>
  <Step title="Install the site connector">
    Run the connector on a host inside your network that can reach every target:

    ```bash
    docker run -d --name tracecat-tunnel --restart unless-stopped \
      -e PANGOLIN_ENDPOINT=<site_endpoint> \
      -e NEWT_ID=<site_id> \
      -e NEWT_SECRET=<site_secret> \
      fosrl/newt
    ```

    To run the binary directly, use `site_install_command`. The connector needs outbound access to the Pangolin endpoint only.
  </Step>
  <Step title="Check the site status">
    ```bash
    curl "https://<tracecat-host>/api/tunnels/<tunnel_id>/status?workspace_id=<workspace_id>" \
      -H "Authorization: Bearer <api_key>"
    ```

    `site_online` turns `true` once the connector connects.
  </Step>
</Steps>

## Bring your own Pangolin

If you already run Pangolin and manage the site, resources, and access yourself, create a machine client in Pangolin, grant it only the resources Tracecat needs, and register it:

```bash
curl -X POST "https://<tracecat-host>/api/tunnels?workspace_id=<workspace_id>" \
  -H "Authorization: Bearer <api_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "onprem-splunk",
    "endpoint": "https://pangolin.example.com",
    "client_id": "<machine_client_id>",
    "client_secret": "<machine_client_secret>",
    "allowed_targets": [{"host": "splunk.internal", "ports": [8089]}]
  }'
```

`endpoint` must use `https`. Tracecat encrypts `client_secret` and never returns it. Keep `allowed_targets` in step with the Pangolin resources; Tracecat enforces both, so a port must appear in each.

## Route actions through a tunnel

Set the tunnel in the action's **Control flow** tab, or set **Default tunnel** in the workflow settings to route every action. An action's own tunnel overrides the workflow default. In a workflow definition, use `tunnel` on the action or `config.tunnel`:

```yaml
config:
  tunnel: onprem-splunk
actions:
  - ref: search_splunk
    action: core.http_request
    args:
      url: https://splunk.internal:8089/services/search/jobs
      method: POST
```

Tracecat checks that the tunnel exists in the workspace and that your organization has the `tunnels` entitlement when you save, publish, and run the workflow. At runtime, the executor issues a short-lived token for the tunnel, sets `HTTP_PROXY` and `HTTPS_PROXY` to the tunnel's gateway, and limits the action's network to that gateway. The action fails if the tunnel is disabled or its gateway isn't available; it never falls back to direct egress. The gateway's allowed targets decide which hosts the action may reach, including private addresses.

Subflows, scatter, gather, loops, AI agent actions, and `core.script.run_python` reject an explicit `tunnel` and ignore the workflow default.

## Run the tunnel gateway

Each tunnel has one gateway that forwards action traffic through Pangolin. Tracecat Cloud runs gateways for you. On Kubernetes, the Helm chart runs them; see [Tunnels](/self-hosting/kubernetes#tunnels).

Elsewhere, such as Docker Compose, run one gateway container per tunnel. Issue its gateway key first. Each new key revokes the previous one and is returned once:

```bash
curl -X POST "https://<tracecat-host>/api/tunnels/<tunnel_id>/gateway-key?workspace_id=<workspace_id>" \
  -H "Authorization: Bearer <api_key>"
# {"tunnel_id": "<tunnel_id>", "gateway_key": "<gateway_key>"}
```

```bash
docker run -d --name tunnel-gateway --cap-add NET_ADMIN --device /dev/net/tun \
  -e PANGOLIN_ENDPOINT=<pangolin_endpoint> \
  -e PANGOLIN_CLIENT_ID=<machine_client_id> \
  -e PANGOLIN_CLIENT_SECRET=<machine_client_secret> \
  -e TRACECAT_TUNNEL_ID=<tunnel_id> \
  -e TRACECAT_TUNNEL_GATEWAY_KEY=<gateway_key> \
  -e TRACECAT_TUNNEL_API_URL=http://api:8000 \
  ghcr.io/tracecathq/tracecat-tunnel-gateway
```

- Allow only executors to reach the gateway on port `8080`, and set `TRACECAT__TUNNEL_GATEWAY_HOST_TEMPLATE` on executors to its hostname.
- Allow outbound TCP 443 and UDP 21820 from the gateway to the Pangolin endpoint.
- Set `TRACECAT_TUNNEL_GATEWAY_BLOCKED_CIDRS` to the internal ranges the gateway must never dial. It always refuses loopback, link-local, cloud metadata, and the Tracecat API's own addresses.
- Restart the gateway with the new key after a key rotation. The gateway applies disabled tunnels and removed targets within 15 seconds.

## Use TLS with private services

Allowed targets limit which host and TCP port a connection opens to, not which application answers on it. The gateway relays TLS without decrypting it, so a client can pick another virtual host on the same IP address and port with SNI or the `Host` header. Don't rely on allowed targets to isolate applications behind a shared reverse proxy; give each one its own address or port, or restrict access at the proxy.

HTTPS through a tunnel stays encrypted end to end. The gateway relays the TLS connection without decrypting it, and the action verifies the server certificate against the hostname in the URL, such as `splunk.internal`. Issue the certificate for the hostname you list in `allowed_targets`.

If an internal CA signs the certificate, add the CA to the workspace:

<Steps>
  <Step title="Create a CA certificate credential">
    In the workspace, open **Credentials** and select **Add credential**. Name the secret `ca_cert`, set **Type** to **CA certificate**, paste the PEM-encoded CA certificate, and select **Create secret**. Tracecat stores it as the `CA_CERTIFICATE` key.

    <Frame>
      <img src="/img/manage-platform/tunnels-ca-certificate.png" alt="Create a CA certificate credential" />
    </Frame>
  </Step>
  <Step title="Keep certificate verification on">
    `core.http_request`, `core.http_poll`, and `core.http_paginate` load the `ca_cert` credential automatically. Leave `verify_ssl` set to `true`; requests then fail if the certificate does not chain to your CA or does not match the hostname.
  </Step>
</Steps>

If the service requires client certificates, add a credential named `mtls` with the **mTLS certificate + key** type. See [Secrets](/automations/core-concepts/secrets) for every credential type.

Plain `http://` requests are encrypted inside the Pangolin tunnel, but not between the site connector and the target, and the gateway can read them. Prefer `https://` for anything that carries credentials.

## Manage tunnels

- List tunnels with `GET /tunnels` and read one with `GET /tunnels/{tunnel_id}`.
- Rename, describe, or disable a tunnel with `PATCH /tunnels/{tunnel_id}`. Managed tunnels reject changes to `endpoint`, `client_id`, `client_secret`, and `allowed_targets`; create a new managed tunnel to change targets.
- Delete a tunnel with `DELETE /tunnels/{tunnel_id}`. For managed tunnels, Tracecat deletes the Pangolin resources, machine client, and site first. If Pangolin cleanup fails, the request returns `502` and keeps the tunnel so you can retry. Stop the site connector afterwards.

## Configure Pangolin for self-hosted Tracecat

Tracecat Cloud manages Pangolin for you, so this section applies only to self-hosted Tracecat. Managed tunnels provision Pangolin through its Integration API.

<Steps>
  <Step title="Enable the Integration API">
    Deploy Pangolin separately and enable its [Integration API](https://docs.pangolin.net). The API base URL ends in `/v1`.
  </Step>
  <Step title="Create an organization API key">
    In the Pangolin dashboard, open your organization's API keys and create a key with these permissions:

    - Sites: pick site defaults, create, get, and delete.
    - Clients: pick client defaults, create, get, and delete.
    - Private resources: create, get, delete, and list resource clients.
  </Step>
  <Step title="Set the Tracecat environment variables">
    Set these on the `api` service and restart it:

    ```bash
    TRACECAT__PANGOLIN_ENDPOINT=https://pangolin.example.com
    TRACECAT__PANGOLIN_API_URL=https://pangolin.example.com/v1
    TRACECAT__PANGOLIN_ORG_ID=<pangolin-org-id>
    TRACECAT__PANGOLIN_API_KEY=<pangolin-org-api-key>
    ```

    Managed tunnels stay off until all four are set. See [Environment variables](/self-hosting/environment-variables).
  </Step>
</Steps>
