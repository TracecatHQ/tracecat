Tracecat's threat model relies on four platform-enforced controls:

- Identity and tenant authorization.
- Deterministic tool policy.
- Sandboxed execution.
- Audit and telemetry.

These controls do not rely on the LLM following instructions. The LLM can propose actions, but Tracecat decides what runs.

This page covers Tracecat Cloud and hardened self-hosted deployments.

## Threat model

This threat model covers the complete Tracecat platform. It includes conventional platform threats and AI-specific threats.

### Protected assets

- Organization and workspace data.
- Agent and automation configuration.
- User and service-account identity.
- API and OAuth credentials.
- MCP and LLM provider credentials.
- External systems reachable through tools.
- Control-plane and executor infrastructure.
- Audit records and agent telemetry.

### Threat actors and untrusted sources

Tracecat assumes risk from:

- External attackers targeting API, authentication, or MCP endpoints.
- Compromised or malicious users and service accounts.
- Attackers who control content consumed by an agent.
- Compromised LLM or API providers.
- Compromised MCP servers.
- Malicious packages and local MCP processes.
- Unsafe LLM output and generated code.

Tracecat treats the LLM as an untrusted decision-maker. It can propose a tool call or generate code. It cannot grant itself a role or approve its own call. It cannot resolve a brokered secret or change sandbox policy.

### Within Tracecat boundary

| Attack surface | How an attacker can use it | Primary Tracecat controls |
| --- | --- | --- |
| Authentication and tenant access | Steal or replay user credentials.<br/>Steal service-account credentials or personal access tokens.<br/>Call API or MCP endpoints as the victim.<br/>Probe identifiers from another workspace. | Authenticate before tenant resolution.<br/>Enforce SSO and RBAC.<br/>Scope service accounts.<br/>Apply tenant scope and PostgreSQL row-level policies. |
| Agent context | Place hostile instructions in prompts or retrieved documents.<br/>Hide instructions in alerts or email.<br/>Hide instructions in cases or tool results.<br/>Redirect the agent goal or induce a high-impact tool call. | Default-deny tool policy.<br/>Trusted-proxy authorization.<br/>Human approval for selected tools.<br/>Credentials kept outside LLM context. |
| Tools and remote MCP | Publish misleading tool metadata.<br/>Return poisoned tool results.<br/>Compromise a remote server to exfiltrate data or trigger unsafe actions. | Captured tool inventory.<br/>Allow and deny policy.<br/>Approval gates.<br/>Trusted API and MCP proxy.<br/>Inherited user permissions for external Tracecat MCP. |
| Generated code and `stdio` MCP | Cause shell or Python code to read files.<br/>Use local MCP code to consume resources.<br/>Reach the network.<br/>Attempt to attack the executor or another run. | nsjail namespaces and syscall filtering.<br/>Read-only runtime and scoped mounts.<br/>cgroup and process limits.<br/>Default-deny agent network. |
| Credentials and secret references | Ask the LLM to expose a credential.<br/>Craft a tool request that tries to resolve or reuse another secret. | Execution-time credential broker.<br/>Policy checks before resolution.<br/>Credential injection outside the sandbox for brokered calls. |
| Human approval | Disguise the purpose of a tool call.<br/>Attempt to resume execution without an authorized decision. | Authenticated approver checks.<br/>Temporal durable execution.<br/>Decision bound to the run.<br/>Per-tool approval audit event. |
| Agent and platform configuration | Use a compromised administrator to widen tool access.<br/>Enable network access or connect a malicious provider.<br/>Persist the change across later runs. | RBAC and tenant scope.<br/>Platform audit events.<br/>Workspace Git sync and repository review. |
| Availability and consumption | Loop LLM or tool calls.<br/>Fork processes.<br/>Fill storage or exhaust memory.<br/>Drive unexpected inference cost. | Wall-time and resource limits.<br/>cgroup memory enforcement.<br/>File and process limits.<br/>Planned token budgets and burn-rate limits. |

### Outside Tracecat boundary

You own controls for systems that Tracecat does not operate.

| Concern | Customer hardening | Suggested tools |
| --- | --- | --- |
| Identity provider | Require MFA and conditional access.<br/>Review session and account-lifecycle policy. | Your identity provider. |
| External LLMs and APIs | Review data use and retention.<br/>Confirm residency and provider access.<br/>Apply provider and endpoint allowlists. | Your LLM and API providers. |
| Prompt and data filtering | Route LLM traffic through an LLM gateway.<br/>Apply prompt-injection and content controls.<br/>Filter PII and sensitive data. | [LiteLLM Proxy](https://docs.litellm.ai/)<br/>[LLM Guard](https://github.com/protectai/llm-guard) |
| MCP policy | Place an independent gateway around MCP traffic.<br/>Apply an allow or deny layer.<br/>Add inspection or consent controls. | [ContextForge](https://github.com/IBM/mcp-context-forge) |
| Detection and retention | Export OTEL data and platform audit events.<br/>Define detections and retention.<br/>Create an incident-response process. | [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/)<br/>[Grafana Alloy](https://grafana.com/docs/alloy/latest/) |
| Git change control | Require reviews and protected branches.<br/>Sign changes to synced configuration. | GitHub<br/>GitLab |
| AI red teaming | Test agents before production.<br/>Retest prompt changes.<br/>Retest LLM and provider changes.<br/>Retest skill, tool, and MCP changes. | [PyRIT](https://github.com/microsoft/PyRIT)<br/>[garak](https://github.com/NVIDIA/garak) |

Tool links are examples, not endorsements.

Use these references when you define customer-owned controls:

## Identity and platform boundaries

<Badge stroke color="gray" size="sm" shape="pill">A01</Badge> <Badge stroke color="gray" size="sm" shape="pill">A07</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI03</Badge>

Tracecat applies these controls:

- API and MCP authentication before tenant context is resolved.
- RBAC through roles, groups, and scoped service accounts.
- Tenant scope in the application and database layers.
- PostgreSQL row-level policies for tenant-owned data.
- Encryption for sensitive settings and stored credentials.
- Application-level encryption for Temporal payloads.
- TLS for production traffic.

### External secrets

<Badge stroke color="gray" size="sm" shape="pill">A04</Badge> <Badge stroke color="blue" size="sm" shape="pill">LLM02</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI03</Badge>

- You can keep workspace and integration credentials in AWS Secrets Manager.
- Tracecat stores credential metadata and resolves values at execution time.
- Trusted proxies receive credentials for API and LLM calls.
- The remote HTTP MCP proxy receives MCP credentials.
- The LLM receives typed interfaces and results instead of credential values.
- Local `stdio` MCP credentials enter the shared sandbox. Treat them as accessible to agent-controlled code.

## Agent and MCP control plane

### Default-deny tool policy

<Badge stroke color="gray" size="sm" shape="pill">A01</Badge> <Badge stroke color="blue" size="sm" shape="pill">LLM06</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI02</Badge>

- Hosted agents apply deterministic policy to Tracecat tools and remote MCP tools.
- The same policy controls normal SDK-dispatched `stdio` MCP calls.
- Agents discover only tools allowed by identity and workspace scope.
- Agent configuration and tool policy narrow that set further.
- An explicit deny overrides an allow.
- The trusted proxy rechecks Tracecat and remote HTTP MCP calls.
- Local `stdio` MCP relies on the captured inventory and sandbox boundary.

Every policy decision has one result:

- `Allow`: Run the tool through the trusted proxy or `stdio` process.
- `Deny`: Block the call before credentials resolve or side effects occur.
- `Require approval`: Create a durable request and pause before execution.

Hosted-agent runs have sandbox wall-time and resource limits. These limits do not assume a fixed number of LLM requests or tool calls.

  Coming soon:

  - A total token budget will bound inference cost per run.
  - A token burn-rate limit will bound consumption velocity.
  - Tool policy and approval will continue to control side-effect risk.
</Info>

### Durable human approval

<Badge stroke color="gray" size="sm" shape="pill">A01</Badge> <Badge stroke color="gray" size="sm" shape="pill">A06</Badge> <Badge stroke color="blue" size="sm" shape="pill">LLM06</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI02</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI09</Badge>

- Temporal persists an agent at the approval boundary.
- The tool waits for an authorized acceptance.
- The decision remains attached across retries and worker restarts.
- Tracecat authorizes the call only when the recorded decision permits it.
- Authenticated UI and API decisions emit one audit event per tool.

Each approval event records:

- Approver and decision time.
- Decision source and tool identifiers.
- Accepted or rejected outcome.
- Override status.
- An optional filtered denial reason.

### External MCP connections

- OAuth connections inherit the user's effective Tracecat permissions.
- Personal access tokens remain workspace-scoped.
- The MCP access page groups connections and tokens by user.
- The page also shows external MCP tool calls.
- Per-profile scope reduction below user permissions is planned.

## Trusted agent execution

<Badge stroke color="gray" size="sm" shape="pill">A05</Badge> <Badge stroke color="gray" size="sm" shape="pill">A06</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI05</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI08</Badge>

- Hosted agents run inside nsjail boundaries.
- Agent-generated code and local MCP processes share that boundary.
- The sandbox exposes only the files and broker interfaces required for the run.
- General automation actions use their configured executor network policy.

| Layer | Control |
| --- | --- |
| Network | Isolated network namespace.<br/>No direct route by default.<br/>LLM and tool requests use trusted brokers.<br/>Direct internet access requires an explicit agent setting. |
| Identity and processes | No host or platform-service identity.<br/>The agent and `stdio` children share one sandbox identity. |
| Namespaces | User and process namespaces.<br/>Mount and IPC namespaces.<br/>Hostname and network namespaces. |
| Filesystem | Read-only runtime and dependencies.<br/>Scoped mounts and bounded temporary storage.<br/>Isolated writable working directory. |
| Kernel boundary | Syscall filtering blocks unnecessary kernel operations.<br/>The process cannot add privileges from inside the jail. |
| Resources | cgroup v2 bounds aggregate memory.<br/>CPU and wall-time limits.<br/>File-size and open-file limits.<br/>Process-count limits. |
| Lifecycle | Cancellation and timeout terminate the sandbox process tree.<br/>Tracecat removes per-run state after execution. |

- These controls reduce the blast radius of compromised output or third-party code.
- They do not make untrusted code safe outside a supported sandbox profile.

### Sandboxed MCP

<Badge stroke color="gray" size="sm" shape="pill">A03</Badge> <Badge stroke color="gray" size="sm" shape="pill">A08</Badge> <Badge stroke color="blue" size="sm" shape="pill">LLM03</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI04</Badge>

- Remote MCP servers run outside the agent sandbox.
- The trusted proxy authenticates remote calls and returns the result.
- `stdio` MCP servers run as children inside the agent sandbox.
- `stdio` processes inherit the sandbox filesystem and network boundaries.
- They also inherit its time, resource, and identity boundaries.
- Normal SDK-dispatched calls use the captured server and tool inventory.
- Local MCP is not a separate policy boundary against direct executable access.
- Use remote HTTP MCP when every call must be rechecked at the trusted proxy.

<Info>
  `stdio` MCP limitations:

  - Approval gates do not support `stdio` tools. Use remote HTTP MCP for approved calls.
  - Enabling `stdio` requires network access for the whole agent sandbox.
  - The agent and `stdio` process share one execution identity.
  - `stdio` credentials enter the shared sandbox.
</Info>

### Trusted API and LLM gateways

- The secure preset-agent path keeps brokered credentials outside LLM context.
- Tracecat resolves a secret only after a permitted request.
- The built-in proxy adds API and OAuth credentials outside the sandbox.
- It adds MCP and LLM credentials outside the sandbox.
- The agent receives the typed result instead of the credential.
- You can use the managed LLM gateway or an OpenAI-compatible provider.
- You can also route LLM traffic through your own proxy.

<Warning>
  - Do not place credentials in prompts or agent inputs.
  - Use preset agents and server-side secret references.
</Warning>

See [Secrets and variables](/agents/secrets-variables) for the preset-agent path and its limitations.

## Auditability and change control

<Badge stroke color="gray" size="sm" shape="pill">A09</Badge> <Badge stroke color="blue" size="sm" shape="pill">LLM10</Badge> <Badge stroke color="purple" size="sm" shape="pill">ASI08</Badge>

Tracecat separates platform audit events from full hosted-agent telemetry.

| Signal | Coverage | Destination |
| --- | --- | --- |
| Platform audit events | Authenticated actor and request source.<br/>Resource, action, and result.<br/>Approval events include the approver and decision time. | Your HTTPS audit webhook.<br/>Tracecat does not store a separate copy of the webhook stream. |
| MCP access activity | OAuth connections and personal access tokens by user.<br/>External Tracecat MCP tool calls. | The MCP access page. |
| Agent OpenTelemetry | Logs, traces, and metrics by tenant and run.<br/>Tool activity and Tracecat approval decisions. | Your OTLP-compatible observability backend. |

- The scoped OTEL relay keeps destination credentials out of the agent runtime.
- You choose the telemetry backend and retention policy.
- Native tool telemetry records the initial tool decision.
- Tracecat records the later human acceptance or rejection.

Platform approval audit events:

- Cover authenticated Tracecat UI and API users.
- Exclude prompts and tool arguments.
- Exclude outputs and overrides.
- Exclude credentials.
- Do not yet include Slack-originated approval actors.
- Use best-effort webhook delivery so collectors cannot block a decision.

### Workspace Git sync

- Use Workspace Git sync for agent and automation configuration.
- Tracecat supports customer-owned GitHub and GitLab repositories.
- Apply review and branch-protection policy in the repository.
- Git history records the configuration promoted into each environment.
- Tracecat RBAC and policy remain the runtime authorization boundary.

## Deployment profiles

| Profile | Isolation contract | Intended use |
| --- | --- | --- |
| Tracecat Cloud | Tracecat manages the secure agent profile and trusted brokers.<br/>Tracecat also manages the network boundary and sandbox lifecycle. | Managed production workloads. |
| Self-hosted Kubernetes | Helm supports nsjail and cgroup-backed isolation.<br/>Apply the required executor security context and capacity settings. | Production workloads that run untrusted code or agents. |
| AWS Fargate | Fargate lacks the kernel capabilities required by nsjail.<br/>Tracecat uses a reduced-isolation executor profile. | Trusted Fargate workloads.<br/>Use Kubernetes for the full sandbox boundary. |
| macOS or Windows development | The direct backend lacks the Linux nsjail boundary. | Local development with trusted code only. |
